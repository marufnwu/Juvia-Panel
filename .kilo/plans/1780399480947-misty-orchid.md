# Plan: Audit & Fix Panel App Creation and Related Functionalities

## Investigation Summary

User reported app creation returns 500 Internal Server Error. After thorough investigation, I found the root cause and several related gaps that need fixing.

## Root Cause of 500 Error

**Frontend sends `build.strategy: "auto"` but the database CHECK constraint only allows:**
```sql
CHECK (build_strategy IN ('nixpacks', 'dockerfile', 'static', 'custom'))
```

The value `"auto"` violates this constraint, causing a SQLite CHECK constraint failure. The error is masked because the handler returns a generic "Failed to create app" message without logging the actual database error.

**Request body (from user's screenshot):**
```json
{
  "name": "sssss",
  "source": { "type": "upload", "branch": "main" },
  "build": { "strategy": "auto" },
  "domain": { "primary": "sss.example.com" }
}
```

## Additional Bugs & Gaps Found

### Backend Issues

1. **No error logging in CreateApp** (apps.go:499-506) - Generic error message hides the actual DB error
2. **No error logging in CreateAppDomain** (apps.go:518-520) - Uses `log.Printf` but only logs, doesn't fail the request
3. **No error logging in CreateDeployment** (apps.go:544-546) - Same issue
4. **`detectRuntime("" , "upload")`** returns "static" - This is fine but may not be what user wants for uploaded apps
5. **No validation for "upload" source type** - Should require a file path or uploaded content
6. **No validation for domain format** - Could store invalid domains
7. **Repository `CreateApp` doesn't handle errors well** - No detailed error context

### Frontend Issues

1. **TypeScript type mismatch** (api.ts:447) - Declares `strategy: 'auto' | 'nixpacks' | 'dockerfile' | 'static'` but backend/database only supports `'nixpacks' | 'dockerfile' | 'static' | 'custom'`
2. **No client-side validation** for the auto → nixpacks mapping
3. **No error detail shown to user** - Just shows "Failed to create app" from backend

### Cross-cutting Issues

1. **Build strategy "auto" not supported** - Either the DB should accept it, or the frontend/backend should map it
2. **Inconsistent build_strategy values** - Frontend says `'auto'` but DB says `'custom'` for the same concept

## Plan

### Step 1: Fix the Build Strategy Mapping (Root Cause)

**Option A: Add "auto" to database CHECK constraint** (simplest, least disruption)
- Update migration to add 'auto' to the allowed values
- This way frontend 'auto' is valid and the backend can handle it

**Option B: Map "auto" → "nixpacks" in backend** (more controlled)
- In the CreateApp handler, if strategy is "auto" or empty, default to "nixpacks"
- Frontend doesn't need to change

**Recommended: Option A + backend default** - Add "auto" to DB constraint AND keep backend default of "nixpacks" for safety.

### Step 2: Add Detailed Error Logging

In `backend/internal/handlers/apps/apps.go`:
- Log the actual database error in `CreateApp` (line 499)
- Log the actual error in `CreateAppDomain` (line 518)
- Log the actual error in `CreateDeployment` (line 544)
- This helps diagnose future issues quickly

### Step 3: Fix Frontend TypeScript Types

In `frontend/src/lib/api.ts`:
- Update `CreateAppInput.build.strategy` type to match backend: `'auto' | 'nixpacks' | 'dockerfile' | 'static' | 'custom'`

### Step 4: Add Input Validation

In `backend/internal/handlers/apps/apps.go`:
- Validate source type is one of: "git", "upload", "docker_compose"
- Validate build strategy is one of the allowed values
- Add validation for domain format (basic check)

### Step 5: Verify Fixes

After implementing, verify:
1. App creation with `strategy: "auto"` works
2. App creation with `strategy: "nixpacks"` works
3. App creation with invalid strategy returns 400 (not 500)
4. Deploy, restart, stop, start work
5. Env vars work
6. Volumes work
7. The error logs show useful information

## Migration Strategy

For existing databases, I need to either:
- Drop and recreate the DB (acceptable for fresh install scenarios)
- Add a new migration that alters the constraint

Since this is a fresh install scenario, updating the original migration is simplest. For production safety, ideally a new migration would be added, but for this user's case (fresh install), updating the existing migration is fine.
